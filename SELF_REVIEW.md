# Self Review

## Слабая часть
Думаю, что слабой частью решения для описания требований является - poC, которая не использует реальную CV-модель.

Face detection, quality score, liveness score и embedding заданы как mock-значения. Поэтому PoC проверяет логику обработки события и принятия решения, но не качество реального распознавания лиц.

## Сделанные предположения

- edge-узел способен выполнять CV/ML pipeline с целевой задержкой p95 до 1 секунды;
- центральный сервис может регулярно обновлять embeddings и access policy на edge;
- для one-to-many поиска в целевой системе используется ANN-индекс;
- исходные изображения не требуется хранить постоянно;
- для сомнительных случаев доступна ручная проверка охраны;
- численные пороги PoC являются демонстрационными и не являются production-порогами.

## Нерешённые риски

- реальное качество обнаружение в условиях проходных;
- устойчивость liveness;
- фактические FAR и FRR;
- работа при большой базе сотрудников;
- работа синхронизации edge при потере сети;
- защита реальных биометрических значений сотрудников.

## Компромиссы ради demo

Для соблюдения ограниченного scope:

- реальные CV-модели заменены mock-значениями;
- ANN-поиск заменён прямым сравнением небольшой demo-базы;
- реальная камера не подключается;
- реальный турникет не подключается;
- интерфейс охраны не реализуется;
- используются только искусственные embeddings.

При этом сохранены два обязательных сценария: автоматический `allow` для happy path и `manual_review` без открытия турникета для risky path.

## Что можно улучшить за два дополнительных дня

За два дополнительных дня я бы:

1. подключила готовые модели детекции и определения лиц;
2. заменила прямой поиск на ANN-индекс;
3. провела измерение latency pipeline;
4. добавила больше тестовых сценариев с различными рисками.

## Что необходимо до production-запуска

- провести валидацию на данных реальных камер;
- выбрать пороги `allow`, `manual_review` и `deny` по FAR/FRR;
- проверить liveness на реальных spoofing-сценариях;
- протестировать нагрузку и latency;
- реализовать безопасную синхронизацию edge и центрального сервиса;
- проверить отзыв доступа сотрудника;
- реализовать защиту и контроль доступа к biometric templates;
- провести проверку безопасности;
- провести юридическую проверку работы с биометрическими данными.

## Что нельзя запускать без отдельной проверки

Без юридической и security-проверки нельзя запускать хранение и обработку реальных биометрических данных сотрудников.

Без валидации нельзя использовать demo-пороги для реального решения `allow`.

Нельзя автоматически пропускать сомнительные случаи с низким качеством, низким liveness или недостаточно уверенным совпадением.

## Что не стоит автоматизировать полностью

Сомнительные случаи должны сохранять ручной контроль.

## Когда проект стоит остановить

Я бы остановила или пересмотрела пилот, если данные покажут, что одновременно не удаётся обеспечить приемлемый уровень безопасности и удобства.
