# ML-часть

Pipeline системы:

```text
face detection
→ quality assessment
→ alignment
→ liveness
→ embedding
→ ANN search
→ decision
```

Сначала нужно найти лицо и проверить, пригоден ли кадр для распознавания.

Для quality важны освещение, уровень размытия, размер лица, ракурс и перекрытия лица. Если качество недостаточное, система не должна пытаться получить уверенный `allow`.

После этого лицо выравнивается по ключевым точкам перед извлечением embedding.

Для первого baseline достаточно готовых предобученных моделей. Обучать собственную face recognition модель для этого проекта не нужно.

Liveness нужен против фото, распечаток и изображений или видео на экране. Проверка выполняется до распознавания. Низкая уверенность liveness означает, что автоматического `allow` быть не должно.


После проверок модель получает embedding лица. На проходной заранее неизвестно, какой именно сотрудник стоит перед камерой, поэтому это задача индификации. ( one-to-many поиск )

Verification был бы нужен, если бы система уже знала предполагаемый `employee_id` и сравнивала лицо только с ним.

Для большой базы полный перебор embeddings не подходит. В целевой системе нужен ANN-индекс. Он возвращает ближайших кандидатов, после чего используются score лучшего кандидата и его margin до второго.

Финальный `allow / manual_review / deny` — это не выход одной модели, а набор правил поверх результатов моделей и access policy.

`allow` возможен, только если:

- лицо найдено;
- качество достаточно;
- liveness пройден;
- match score достаточно высокий;
- margin до второго кандидата достаточный;
- сотруднику разрешён доступ.

Неуверенная зона уходит в `manual_review`.

Если надёжного совпадения нет или доступ сотрудника отозван, возвращается `deny`.

## Пороги и метрики

Конкретные пороги из PoC  нужно настраивать на validation set.

Основные метрики:

- FAR — ошибочные допуски;
- FRR — ошибочные отказы;
- EER;
- ROC/PR;
- latency.

False accept здесь дороже false reject, потому что означает допуск постороннего. Поэтому порог `allow` в первую очередь должен ограничивать FAR.

При этом слишком строгий порог увеличит FRR, очередь и количество `manual_review`, поэтому между уверенным `allow` и `deny` нужна отдельная зона ручной проверки.

## Baseline

Первым я бы проверяла простой pipeline из:

- готового face detector;
- quality check;
- alignment;
- готового anti-spoofing/liveness решения;
- готовой модели embeddings;
- ANN-поиска;
- правил по score, margin и access policy.

Главное на первом этапе — не обучать новую модель, а понять, работает ли такой baseline на реальных камерах кампуса.

## Validation set

Validation set должен отражать реальные условия проходных:

- разные камеры;
- разные дни;
- нормальное и сложное освещение;
- разные ракурсы;
- очки, маски, головные уборы;
- плохие кадры.

## LLM

LLM в контуре `allow / deny` не нужен.

Решение о физическом доступе должно быть воспроизводимым и строиться на CV/ML результатах, порогах и access policy.
